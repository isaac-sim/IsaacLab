Reinforcement Learning
======================

Isaac Lab provides one workflow for training and evaluating policies across several reinforcement
learning (RL) libraries. This page takes you from choosing a library to running, monitoring, and
debugging an experiment.

The shortest path
-----------------

From the Isaac Lab repository, train the Cartpole policy:

.. code-block:: bash

   uv run isaaclab train --rl_library rsl_rl --task Isaac-Cartpole

Training writes checkpoints and TensorBoard logs under ``logs/rsl_rl/``. Evaluate the newest
compatible checkpoint in an interactive visualizer:

.. code-block:: bash

   uv run isaaclab play --rl_library rsl_rl --task Isaac-Cartpole \
       --checkpoint latest --num_envs 32 --viz kit

The ``train`` and ``play`` commands are the Isaac Lab 3.0 entry points for every supported RL
library. The older per-library scripts under ``scripts/reinforcement_learning/`` are deprecated.
Use suffixless task names such as ``Isaac-Cartpole``; the command resolves the configured backend
and play variant for you.

Before a long run
~~~~~~~~~~~~~~~~~

Verify the environment and configuration with a short, small experiment:

.. code-block:: bash

   # Check that the task resets and steps without an RL library.
   uv run isaaclab random_agent --task Isaac-Cartpole --num_envs 16

   # Check the complete training path.
   uv run isaaclab train --rl_library rsl_rl --task Isaac-Cartpole \
       --num_envs 64 --max_iterations 10

If both commands succeed, remove the smoke-test overrides and use the task's tuned defaults.

.. _choose-an-rl-library:

Choose an RL library
--------------------

The table describes the features exposed by the **Isaac Lab integrations**, which can be narrower
than the features of the upstream libraries.

.. list-table::
   :widths: 15 26 30 29
   :header-rows: 1

   * - Library
     - Best starting point for
     - Why you would choose it
     - Isaac Lab notes
   * - **RSL-RL (default)**
     - Fast GPU-parallel locomotion and manipulation
     - PPO with native Isaac Lab Python configs, recurrent and CNN policies, symmetry augmentation,
       random network distillation, and teacher-student distillation
     - Included in the standard ``uv`` environment; supports distributed training
   * - **skrl**
     - Research that needs framework or multi-agent flexibility
     - Switch for JAX, AMP, or explicit IPPO/MAPPO multi-agent training; the upstream project also
       provides a broad collection of algorithms
     - Optional ``skrl`` extra; Isaac Lab exposes PPO, AMP, IPPO, and MAPPO with PyTorch or JAX
   * - **RL-Games**
     - Existing RL-Games experiments and population-based workflows
     - Switch for RL-Games PPO, SAC, or A2C configs, population-based training, or an existing
       RL-Games checkpoint and tooling stack
     - Optional ``rl-games`` extra; supports distributed training and Ray integration
   * - **Stable-Baselines3**
     - Familiar, approachable baselines and ecosystem tooling
     - Switch for the Stable-Baselines3 callback, logging, and model ecosystem, especially for
       smaller or CPU-oriented experiments
     - Optional ``sb3`` extra; the maintained Isaac Lab training entry point uses PPO and does not
       support distributed training
   * - **RLinf**
     - Reinforcement learning fine-tuning of Vision-Language-Action models
     - Switch for distributed GR00T or OpenVLA post-training with Ray and FSDP
     - Specialized installation and workflow; see :ref:`rlinf-post-training`

For a new conventional robotics task, use **RSL-RL** unless a row above gives you a concrete reason
to switch. Do not compare libraries only by a single throughput number: their task configs can use
different rollout lengths, batch sizes, networks, and normalization. Benchmark the configuration
you intend to use with the same task, device, seed, environment count, and total samples.

Install an optional library by selecting its ``uv`` extra on every command:

.. code-block:: bash

   uv run --extra skrl isaaclab train --rl_library skrl --task Isaac-Cartpole
   uv run --extra rl-games isaaclab train --rl_library rl_games --task Isaac-Cartpole
   uv run --extra sb3 isaaclab train --rl_library sb3 --task Isaac-Cartpole

The legacy installer remains available for installations that require it. See
:ref:`installation-legacy-installer` rather than translating the examples on this page to
``isaaclab.sh`` manually.

Configure the experiment
------------------------

Each registered task points to one or more library-specific agent configurations. Keep their
formats separate:

* RSL-RL uses Python config classes derived from ``RslRlBaseRunnerCfg``.
* RL-Games, skrl, and Stable-Baselines3 use library-specific dictionaries or YAML files.
* RLinf uses its dedicated VLA post-training configuration.

The task registration connects a library to its default agent config. For example:

.. code-block:: python

   gym.register(
       id="Isaac-Cartpole",
       entry_point="isaaclab.envs:ManagerBasedRLEnv",
       disable_env_checker=True,
       kwargs={
           "env_cfg_entry_point": f"{__name__}.cartpole_manager_env_cfg:CartpoleEnvCfg",
           "rsl_rl_cfg_entry_point": (
               f"{agents.__name__}.rsl_rl_ppo_cfg:CartpolePPORunnerCfg"
           ),
           "default_agent": "rsl_rl",
       },
   )

Use a string entry point so importing the task does not eagerly import the RL library or config.
Start from the closest maintained config under
``source/isaaclab_tasks/isaaclab_tasks/<task-family>/.../agents/`` instead of creating a config
from scratch.

Discover tasks and agent configs
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

List registered tasks, then inspect the task-specific command help:

.. code-block:: bash

   uv run python scripts/environments/list_envs.py
   uv run isaaclab train --rl_library rsl_rl --task Isaac-Cartpole --help

Use ``--agent`` when a task registers an alternate config. This Cartpole example selects RSL-RL's
symmetry-augmentation config:

.. code-block:: bash

   uv run isaaclab train --rl_library rsl_rl --task Isaac-Cartpole \
       --agent rsl_rl_with_symmetry_cfg_entry_point \
       --run_name ppo_with_symmetry

Task help also reports compatibility between agents and observation or action presets when the
task declares it. Always use an agent whose network matches the selected observation preset.

Override configuration with Hydra
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Append environment and agent overrides after the regular CLI arguments. Library config schemas
are different, so confirm the path in the selected config before overriding it:

.. code-block:: bash

   uv run isaaclab train --rl_library rsl_rl --task Isaac-Cartpole \
       --seed 2024 --run_name cartpole_seed_2024 \
       env.actions.joint_effort.scale=10.0 \
       agent.algorithm.learning_rate=0.0005

See :doc:`/source/features/hydra` for quoting rules, list values, and multirun sweeps.

Choose physics, rendering, and domain presets
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Isaac Lab 3.0 tasks can expose named preset selectors. Append selectors without leading dashes:

.. code-block:: bash

   uv run isaaclab train --rl_library rsl_rl --task Isaac-Cartpole \
       physics=newton_mjwarp

   uv run isaaclab train --rl_library rsl_rl \
       --task Isaac-Cartpole-Camera-Direct \
       physics=newton_mjwarp renderer=newton_renderer presets=rgb

Not every task supports every backend. See :doc:`/source/concepts/backends_and_presets` to discover
the presets declared by a task.

.. important::

   Observation and action presets can change the policy architecture. Use the same ``physics``,
   ``renderer``, domain, and observation/action presets for training and playback. A mismatched
   observation preset commonly fails while loading the checkpoint because tensor shapes differ.

Train efficiently
-----------------

Isaac Lab collects experience from many environments in parallel. ``--num_envs`` controls the
number of independent simulation instances. More environments can improve sample collection, but
only until simulation time, optimizer batch structure, or GPU memory becomes the bottleneck.

Use this progression:

1. Validate resets, observations, rewards, and actions with tens of environments.
2. Run a short training smoke test and inspect reward and episode-length metrics.
3. Increase ``--num_envs`` while measuring steps per second and peak memory.
4. Tune rollout length and mini-batches together when changing the amount of collected data.
5. Scale to multiple GPUs only after one GPU trains correctly.

Headless training is the fastest default; no visualizer flag is necessary:

.. code-block:: bash

   uv run isaaclab train --rl_library rsl_rl --task Isaac-Cartpole

Use a visualizer only for a small debugging run:

.. code-block:: bash

   uv run isaaclab train --rl_library rsl_rl --task Isaac-Cartpole \
       --num_envs 32 --viz kit

For distributed RSL-RL, RL-Games, or skrl training, use the maintained launcher described in
:doc:`/source/features/multi_gpu`.

Camera observations
~~~~~~~~~~~~~~~~~~~

Rendering and image rollouts consume substantially more memory than state observations. Begin with
lower resolution, fewer environments, and a small network. ``--video`` enables the cameras required
to record a perspective view; task cameras used as policy observations still need the task's camera
configuration and matching renderer preset.

Record periodic training clips:

.. code-block:: bash

   uv run --extra video isaaclab train --rl_library rsl_rl \
       --task Isaac-Cartpole --video --video_length 200

For image-like scene sensor outputs, use ``--capture_env_sensors``. See
:doc:`/source/how-to/capture_sensor_frames` for capture intervals and output formats.

Monitor a run
-------------

Start TensorBoard in a second terminal:

.. code-block:: bash

   uv run python -m tensorboard.main --logdir logs

Watch trends, not a single iteration. The most useful first signals are:

* **Mean reward:** should improve for a correctly shaped task, although its absolute value is
  task-specific.
* **Mean episode length:** interpret it with the termination design. Longer is desirable for a
  balance task but not necessarily for a goal-completion task.
* **Throughput:** a large drop after changing environment count, sensors, or rendering points to a
  systems bottleneck rather than an RL problem.
* **Policy loss, value loss, entropy, KL, and action standard deviation:** use these together to
  spot stalled exploration or overly large updates; their names differ by library.

RSL-RL prints collection and learning time, steps per second, losses, mean reward, mean episode
length, total timesteps, and ETA for every learning iteration. RL-Games separates environment-step,
inference, and total throughput. Stable-Baselines3 groups rollout, timing, and optimization metrics.
skrl presents a compact progress display while detailed metrics are available in its logs.

Evaluate and resume
-------------------

Every new training run writes a ``run.json`` manifest. The unified commands use it to find a
checkpoint compatible with the chosen library, task, and agent configuration.

.. list-table::
   :widths: 22 78
   :header-rows: 1

   * - Selector
     - Behavior
   * - ``latest``
     - Selects the highest-step checkpoint from the newest compatible local run.
   * - ``best``
     - Prefers the library's best or final checkpoint; falls back to ``latest`` when the library
       does not write a distinct best checkpoint.
   * - ``pretrained``
     - Downloads a published policy for a supported core-task and backend combination.
   * - ``/path/to/checkpoint``
     - Loads the exact local or retrievable checkpoint path.

Play the best local checkpoint and record a short clip:

.. code-block:: bash

   uv run --extra video isaaclab play --rl_library rsl_rl \
       --task Isaac-Cartpole --checkpoint best --num_envs 32 \
       --video --video_length 200

Resume training from the newest compatible checkpoint:

.. code-block:: bash

   uv run isaaclab train --rl_library rsl_rl --task Isaac-Cartpole \
       --checkpoint latest

When using an explicit checkpoint, repeat the original task, agent, and preset selectors. A
checkpoint only contains the policy state expected by its library; it does not make incompatible
environment observations or actions compatible.

.. _pretrained-checkpoints:

Pretrained checkpoints
~~~~~~~~~~~~~~~~~~~~~~

Published checkpoints cover selected core tasks and declared backend combinations, not every
registered task. If ``--checkpoint pretrained`` reports that no artifact is available, train the
task locally and use ``latest`` or an explicit path.

Published filenames use this scheme:

.. code-block:: text

   <task_name>_<physics_backend>_<render_backend>_<rl_library>.<extension>

For example, ``Isaac-Cartpole_newtonmjwarp_none_rsl_rl.pt`` is a state-based RSL-RL policy trained
with Newton MJWarp. State-only tasks use ``none`` for the render backend. Pass the same selectors
when loading the policy:

.. code-block:: bash

   uv run isaaclab play --rl_library rsl_rl --task Isaac-Cartpole \
       --checkpoint pretrained physics=newton_mjwarp

Specialized workflows
---------------------

RSL-RL distillation
~~~~~~~~~~~~~~~~~~~

Train a teacher, then select the registered distillation agent and load the teacher checkpoint:

.. code-block:: bash

   uv run isaaclab train --rl_library rsl_rl \
       --task Isaac-Velocity-Flat-AnymalD

   uv run isaaclab train --rl_library rsl_rl \
       --task Isaac-Velocity-Flat-AnymalD \
       --agent rsl_rl_distillation_cfg_entry_point \
       --checkpoint /path/to/teacher.pt

skrl multi-agent and JAX training
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Use skrl when the task needs MAPPO or IPPO, or when the policy must be trained with JAX:

.. code-block:: bash

   uv run --extra skrl isaaclab train --rl_library skrl \
       --task Isaac-Shadow-Handover-Direct --algorithm MAPPO

   uv run --extra skrl isaaclab train --rl_library skrl \
       --task Isaac-Reach-Franka --ml_framework jax

Install a CUDA-enabled JAX build appropriate for the platform before using the JAX workflow. JAX
preallocates GPU memory by default, so coordinate its memory settings with simulation memory. See
the `skrl installation guide <https://skrl.readthedocs.io/en/latest/intro/installation.html>`__ and
the `JAX installation guide <https://docs.jax.dev/en/latest/installation.html>`__.

RLinf VLA post-training
~~~~~~~~~~~~~~~~~~~~~~~

RLinf is not a drop-in replacement for the conventional task commands above. It accepts a VLA
configuration and base model path:

.. code-block:: bash

   uv run --extra rlinf isaaclab train --rl_library rlinf \
       --config_name isaaclab_ppo_gr00t_assemble_trocar \
       --model_path /path/to/base_model

Follow :ref:`rlinf-post-training` for installation, distributed execution, and evaluation.

Programmatic use
----------------

Applications can call the same dispatcher without creating an ``argparse.Namespace``:

.. code-block:: python

   from isaaclab_rl import TrainingRequest, train

   train(TrainingRequest(backend="rsl_rl", task="Isaac-Cartpole", max_iterations=100))

Use :class:`~isaaclab_rl.entrypoints.PlaybackRequest` with
:func:`~isaaclab_rl.entrypoints.play` for playback. Put backend-specific options in
``backend_args`` and Hydra or preset selectors in ``hydra_args``.

Troubleshoot training
---------------------

Out of memory
~~~~~~~~~~~~~

Reduce ``--num_envs`` first. For camera tasks, also reduce image resolution, captured views,
rollout length, or network size. Disable the interactive visualizer during performance runs. Asset
collision complexity and deformable bodies also increase simulation memory independently of the
policy.

NaNs in observations or the policy
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

NaNs usually originate in an unstable simulation or an invalid reset and then propagate into the
learner. Reproduce the failure without training and inspect the first non-finite value. Check:

* reset joint positions, velocities, and object poses;
* actuator gains, effort and velocity limits, and action scaling;
* contact geometry, masses, inertias, and large impulses;
* physics time step, substeps, and solver iterations; and
* reward or observation terms with unsafe division, normalization, or square roots.

Do not hide the source by clamping every policy input. Fix invalid simulation state or term math,
then repeat the short smoke test.

Training is stable but does not learn
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Confirm the environment contract before tuning PPO: actions affect the intended joints,
observations change, rewards reflect progress, and success/failure terminations occur when expected.
Compare against the closest maintained task config, then change one factor at a time. Record the
task, library, physics and renderer presets, seed, environment count, agent entry point, and Hydra
overrides for every comparison.

Checkpoint does not load
~~~~~~~~~~~~~~~~~~~~~~~~

Verify the RL library, task, ``--agent``, observation/action presets, physics/domain configuration,
and ML framework. Policy shape errors almost always mean one of these differs from training. Prefer
``latest`` or ``best`` because manifest discovery filters incompatible runs before loading.
